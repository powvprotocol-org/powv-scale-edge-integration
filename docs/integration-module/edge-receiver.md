# Edge Receiver

The Edge Receiver is the embedded endpoint of the PoWV Scale-to-Edge Integration Module.

In the current laboratory implementation, an ESP32-based node receives structured measurement events produced by the host acquisition layer, acknowledges successful delivery, retains the latest event in runtime memory, and exposes the event through a local inspection interface.

Its role is to provide the first embedded execution point after event construction and network transport.

---

## Position in the Integration Flow

**Physical Weighing Event → Measurement Instrument → Host Acquisition Layer → Structured Event → SHA-256 Integrity Identifier → Wi-Fi / HTTP Transport → ESP32 Edge Receiver → Local API → Inspection Dashboard**

The ESP32 operates downstream of the host acquisition process.

The host is currently responsible for acquiring the physical measurement, interpreting the instrument response, normalizing the resulting values, constructing the structured event, generating the SHA-256 integrity identifier, and transmitting the event.

The Edge Receiver begins operating after that structured event reaches the embedded layer.

---

## Current Implementation

The laboratory receiver is based on an ESP32-class microcontroller with integrated Wi-Fi connectivity.

The current implementation provides four primary functions:

1. Receive a structured event from the host.
2. Return an application-level acknowledgment.
3. Retain the most recently received event in runtime memory.
4. Expose that event to local clients through a lightweight web interface.

The receiver therefore operates as both an embedded ingestion point and an observability surface for the Scale-to-Edge PoC.

---

## Runtime Flow

A successful event cycle follows this sequence:

**Host Adapter → Structured Event → Network Transport → ESP32 HTTP Receiver → Event Acceptance → Latest-Event State → Application Acknowledgment → Local Inspection**

This flow has been validated using measurements generated by a real physical weighing instrument.

The transition is significant because the event moves from the host-side acquisition environment into an independent embedded device connected through the local network.

---

## Event Ingestion

The ESP32 receives the structured event generated by the host-side integration layer.

The current event representation contains measurement data, contextual information, processing status, and integrity metadata.

A representative event includes the following fields:

| Field                     | Example                     | Function                                       |
| ------------------------- | --------------------------- | ---------------------------------------------- |
| `event_type`              | `weight_measurement`        | Identifies the event class                     |
| `timestamp`               | `2026-09-18T16:26:02`       | Records event construction time                |
| `device.instrument`       | `commercial_weighing_scale` | Identifies the measurement source class        |
| `device.edge_node`        | `edge-node`                 | Identifies the logical edge destination        |
| `measurement.weight_kg`   | `0.082`                     | Normalized physical measurement                |
| `measurement.tare_kg`     | `0.0`                       | Tare associated with the measurement           |
| `commercial.price_per_kg` | `200.0`                     | Optional commercial context                    |
| `commercial.total`        | `16.4`                      | Derived commercial value                       |
| `source`                  | `physical_scale`            | Identifies the source category                 |
| `status`                  | `captured`                  | Indicates processing state                     |
| `integrity.algorithm`     | `SHA-256`                   | Identifies the digest algorithm                |
| `integrity.hash`          | `<event-digest>`            | Integrity identifier associated with the event |

The Edge Receiver operates on this normalized representation rather than on the native serial representation generated by the physical instrument.

That distinction creates a clean boundary between device integration and edge processing.

---

## Application-Level Acknowledgment

After accepting an event, the ESP32 returns an acknowledgment to the host application.

The current acknowledgment contains the logical equivalent of:

| Field      | Value       |
| ---------- | ----------- |
| `received` | `true`      |
| `device`   | `edge-node` |

The acknowledgment confirms that the event reached the embedded application and was accepted by the receiver.

In the current laboratory implementation, this acknowledgment represents successful application-level delivery.

It does not yet represent cryptographic verification of the measurement source.

---

## Latest-Event State

The ESP32 retains the most recently received event in runtime memory.

The current state transition can be represented as:

**Incoming Event N → Replace Current Runtime Event → Latest Event = Event N**

When a new event arrives, it becomes the current event exposed by the receiver.

This simple state model provides immediate observability during integration testing and allows the embedded node to be inspected independently from the host acquisition interface.

The current implementation is focused on latest-event state rather than persistent event history.

---

## Local Event Retrieval

The latest structured event can be retrieved directly from the ESP32 through the local inspection interface.

The interaction is:

**Local Client → Request Latest Event → ESP32 → Structured Event Response → Local Client**

This provides a second observation point for the same event.

The event is first observable in the host acquisition layer and later observable directly from the embedded receiver after successful network transport.

This confirms that the event has traversed the host-to-edge portion of the integration path.

---

## Local Dashboard

The ESP32 also provides a lightweight browser-based dashboard for human-readable inspection of the latest received event.

The current interface can present:

* measured weight;
* tare;
* unit price where available;
* calculated total;
* event timestamp;
* instrument metadata;
* edge-node metadata;
* location context;
* SHA-256 integrity identifier;
* structured event information.

The dashboard periodically retrieves the latest event from the Edge Receiver and updates the displayed state as new measurements arrive.

The visualization layer does not create or modify the physical measurement. It renders the event already held by the embedded node.

The resulting relationship is:

**ESP32 Runtime State → Local Interface → Browser Dashboard**

---

## Edge Runtime Model

The current receiver behavior can be summarized as:

`receive(event) → latest_event = event → acknowledge() → serve(latest_event)`

At the application level, the receiver follows four basic operations:

| Operation       | Behavior                                              |
| --------------- | ----------------------------------------------------- |
| Event reception | Accept the structured event submitted by the host     |
| Runtime update  | Replace the current latest-event state                |
| Acknowledgment  | Return successful receipt status                      |
| Inspection      | Return the current event to a requesting local client |

This model represents the behavior implemented during the current laboratory stage.

---

## HTTP Role

HTTP is currently used as the application transport between the host and the ESP32 over the local Wi-Fi network.

The transport path is:

**Host Application → HTTP Request → Wi-Fi Network → ESP32 Web Server**

The event body contains the structured measurement event generated upstream by the host adapter.

The ESP32 web server processes the incoming request, stores the event payload, and returns the application acknowledgment.

For inspection, the same embedded web server makes the latest event available to a local client and serves the browser-based dashboard.

This means the current ESP32 operates simultaneously as:

* an event-ingestion endpoint;
* a latest-event state holder;
* a machine-readable event source;
* a lightweight visualization server.

---

## Integrity Position

The event arriving at the ESP32 already contains a SHA-256 integrity identifier generated by the host-side event construction layer.

The current integrity path is:

**Structured Event → Canonical Representation → SHA-256 → Event + Integrity Identifier → ESP32**

Using the PoWV notation:

`P = canonical structured event`

`H = SHA256(P)`

The host currently performs the calculation of `H` before the event is transmitted.

The ESP32 receives both `P` and the associated `H`.

Therefore, the current relationship is:

**Host: `P → SHA256(P) → H`**

followed by:

**ESP32: `Receive(P + H)`**

At this stage, the edge node transports and exposes the integrity metadata but does not yet independently recalculate the digest.

---

## Next Edge Verification Stage

The next validation milestone is independent SHA-256 verification at the ESP32.

The intended processing sequence is:

**Receive P + H → Reconstruct Canonical P → Calculate SHA256(P) → Compare Local Digest with Received H → Produce Verification Result**

The expected comparison is:

`H_local == H_received`

If both values match, the Edge Receiver can confirm that the structured representation used during local verification corresponds to the integrity identifier received with the event.

This changes the embedded role from passive event receipt to active integrity verification.

The progression is therefore:

| Stage   | Edge Responsibility                                  |
| ------- | ---------------------------------------------------- |
| Current | Receive event and integrity identifier               |
| Next    | Recalculate and compare SHA-256 digest               |
| Later   | Verify authenticated event origin                    |
| Later   | Integrate hardware-backed cryptographic identity     |
| Later   | Participate in durable audit and anchoring workflows |

## Relationship to the PoWV Event Model

Within the current Scale-to-Edge implementation, the Edge Receiver appears after the following stages:

**E → M → P → H → Edge**

| Symbol | Meaning                                                                 |
| ------ | ----------------------------------------------------------------------- |
| `E`    | Physical event                                                          |
| `M`    | Measurement produced by the physical instrument                         |
| `P`    | Structured digital representation                                       |
| `H`    | SHA-256 integrity identifier                                            |
| `Edge` | Embedded event receipt, state retention, acknowledgment, and inspection |

The ESP32 therefore represents the first embedded consumer of the normalized event in the current laboratory architecture.

The broader PoWV model extends beyond this stage:

**E → M → P → σ → V → H → A → I**

where subsequent stages introduce cryptographic attestation, verification, audit anchoring, and downstream interpretation.

## Current Laboratory Result

The Scale-to-Edge laboratory test demonstrated a complete host-to-embedded event transfer using data derived from a real physical measurement.

The demonstrated sequence was:

1. A real weighing event was generated.
2. The measurement was acquired by the host.
3. Measurement values were normalized.
4. A structured event was created.
5. A SHA-256 integrity identifier was generated.
6. The event was transmitted over Wi-Fi using HTTP.
7. The ESP32 received the event.
8. The receiver returned a successful acknowledgment.
9. The event became the latest embedded runtime state.
10. A local client retrieved the event from the ESP32.
11. The dashboard rendered the received measurement and associated metadata.

This establishes a functional transition from physical instrumentation to embedded event processing.

## Engineering Significance

The Edge Receiver establishes a practical boundary between host-side event construction and embedded processing.

Before transmission, the measurement exists within the physical instrument and the host-side software environment.

After successful receipt, the structured representation of that measurement exists inside an independent embedded node connected through the local network.

The current implementation therefore establishes the following transition:

**Physical Instrument → Host Event Representation → Network Transport → Embedded Runtime State**

This provides the technical foundation for subsequent capabilities including:

* edge-side integrity verification;
* authenticated device identity;
* cryptographic attestation;
* secure-element integration;
* replay protection;
* authenticated transport;
* persistent evidence handling;
* audit anchoring;
* downstream validation.

The ESP32 Edge Receiver is therefore not only a visualization endpoint. It is the first embedded processing boundary in the current PoWV Scale-to-Edge integration path.
